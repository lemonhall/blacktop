# BLACKTOP 架构

写给架构师看的版本：**这套东西由谁负责哪一段、边界为什么划在那里**。

如果你只想知道"一局比赛打了哪些请求"，看 [flow.md](./flow.md)；
想知道每个报文的字段含义，看 [protocol.md](./protocol.md)。

---

## 1. 一句话

BLACKTOP 是一个**服务器权威**的在线摩托竞速：十五台车挤一条路，两名人机混战，
路上还有同向车流和迎面而来的大运。后端跑在 Cloudflare Workers + Durable Objects
上，前端是一组静态文件（Vercel、Cloudflare Pages 或同一个 Worker 的资源绑定都行）。

底层是一个共享的确定性内核：**同一段 `stepRacer()` 同时在服务端和浏览器里跑**。
服务端是真相，浏览器用它做本地预测。

## 2. 三层，职责不重叠

```
┌─────────────────────────────── 浏览器 ───────────────────────────────┐
│ web/  渲染 · 输入采样 · 本地预测(只预测自己) · 对账 · HUD · 屏幕状态  │
│        ↑ 读同一份内核                                                │
│ sim/  确定性内核：赛道生成 · 车手物理 · 车流/大运 · AI · 线协议编解码 │
└───────────────────────────────┬──────────────────────────────────────┘
                    WebSocket（对局） / HTTP（大厅、身份、战绩）
┌───────────────────────────────┴────────────  Cloudflare ────────────┐
│ src/index.mjs   Worker 入口：认租户 → 认令牌 → 路由 → CORS，无状态    │
│ src/room.mjs    Room DO：一局对局的权威世界（模拟 + 名册 + 广播）     │
│ src/lobby.mjs   Lobby DO：一个租户的房间目录（强一致的"现在有哪几间"）│
│ D1             租户注册表 + 历史战绩（排行榜是 SQL 在 JSON 上聚合）   │
└──────────────────────────────────────────────────────────────────────┘
```

三样东西只有一份实现，前后端都 import：

| 共享内核文件 | 里面是什么 | 谁在用 |
|---|---|---|
| `sim/track.mjs` | 由 `seed + mode` 生成同一条路（曲率 / 坡度 / 车道坐标） | 服务端造世界、浏览器画路 |
| `sim/racer.mjs` | 单车物理：油门、压车、离心（出拳与撞车在同目录的另两间） | 服务端逐格推进、浏览器本地预测 |
| `sim/wire.mjs` | 世界 ↔ JSON 的编解码 | 服务端发、浏览器解 |

`tools/build.mjs` 把 `sim/` 原样拷进 `web/sim/`——前端用 `/sim/xxx.mjs` 直接
import，**没有打包器、没有转译、没有第二份副本**。改一处两边一起改，忘了同步
这件事在结构上就不可能发生。

## 3. 后端负责什么

**Worker（`src/index.mjs`）** 是门口的接待，只做四件事：认租户、认令牌、
把请求转给对的 Durable Object、给浏览器补 CORS。它**不做任何游戏判定**——
Worker 的实例可以被复制到任意边缘节点，把"谁先冲线"放在这里等于让它有好几个
互相看不见的副本。

**Room（`src/room.mjs`）** 是权威世界。一场对局的全生命周期都在一个对象里：
名册与闸门（`room-state.mjs`）、连接与上行消息（`room-conns.mjs`）、
开局与中途进出（`room-match.mjs`）、节拍器（`room-ticker.mjs`）、
时间算术（`room-clock.mjs`）。它拿到的输入只有一种：**玩家上行的命令**。

**Lobby（`src/lobby.mjs`）** 是一个租户一个实例的房间目录。目录要的是
"强一致的一览"——每个房间各写各的 KV，列表页必然出现重复、幽灵房间和过期人数。

**D1** 存两样：`tenants`（租户注册表与配额规则）、`matches`（历史战绩）。
排行榜直接在每场比赛的 JSON 明细上用 SQLite 的 `json_each` 聚合，
不为"一场比赛的参赛者"再建一张明细表——那只会多一次 JOIN 和一份同步负担。

## 4. 前端负责什么

前端不是"把服务端状态画出来"的终端，它有两件真正的活：

1. **本地预测**：以 60Hz 跑自己那台车（`web/js/predict.mjs`）。跑的是同一个
   `stepRacer()`，所以只要输入一致，算出来的路径和服务端逐米相同。
   **只预测自己**：车流、撞车、被人挤开、出拳打到谁一概不预测——那些必须听
   权威端，否则会出现"我这边把他踹翻了、他那边骑得好好的"。
2. **插值渲染**：渲染头比权威世界时间**晚 140ms**（`web/js/view.mjs`）。
   这 140ms 是拿操作手感换画面平滑的那笔交易，它必须盖得住链路上最长的帧间隔。

其余是常规 UI：房间列表 4 秒轮询（列表慢一点没人受伤，为它维持常驻连接不值）、
输入采样、播报、HUD、结算页。有一条约定贯穿全部界面代码：
**界面跟着服务端走**——收到 `room` 说还在 staging，哪怕我已经切到赛道上，
也要乖乖切回候场。

## 5. 一局对局的状态机

```
        POST /rooms                 WS socket                {t:"start"}
  ∅ ──────────────────▶ staging ───────────────▶ live ──────────────▶ over
                        候场：名册/举手/          跑：60Hz 模拟         结算：名次+赏金
                        机器人/选车/赛道          20Hz 快照             ↓ 房主 "reset"
                              ▲                                          │
                              └──────────────────────────────────────────┘
```

- `staging`：谁在房里、谁举手了、房主放几个机器人、选哪条赛道。**开局有闸门**：
  房主点"出发"之前，所有人类必须举手（房主的按钮就是他的表态，服务端会拒掉
  房主的 `ready`），否则回一条 `error: not_ready` 并附上还没举手的人名。
- `live`：世界以 60Hz 固定步长推进，50ms 一张快照。默认允许**中途加入**——
  新人落在领跑者身后 45 米、速度取全场平均（看得见尾灯，追得上，但没占便宜）。
  房主也可以把"中途加入"关掉，那时开跑之后新人只会收到 `join_closed`。
- `over`：`settle()` 算名次、发赏金、**把世界停表**。房主点"再来一局"回到
  `staging`，并且**清空所有人的举手状态**——上一局的 ready 不能顺延。

房间的回收判据只有两条（`room-clock.mjs#reclaimReason`）：连接全断，或者
连着却整整 30 分钟一条消息都没来。**不看名册有没有动过**：一局从头发到尾名册
本来就不动，拿它当判据的后果是"跑到第十分钟房间把自己拆了"。

## 6. 时间：为什么没有常驻定时器

世界推进的驱动有三个，谁先来都行，踩的都是同一个 50ms 网格：

| 驱动 | 触发时机 | 为什么需要它 |
|---|---|---|
| 上行消息 | 玩家 25Hz 的命令 / 2 秒的心跳 | 主驱动，延迟最低 |
| `setTimeout` 节拍器 | 每拍复用一条计时链 | 没有输入时世界也别停 |
| Durable Object alarm | 5 秒一次的兜底 | 实例被冻过、计时器被节流时的保险 |

两条硬规矩写在 `room-ticker.mjs` 里，都是"幻灯片事故"换来的：

1. 世界的时刻取**网格上该到的时刻**，不取计时器实际醒来的时刻（workerd 的
   `setTimeout(50)` 实测平均 62ms 才醒，按实际时刻推进世界比墙上时钟快 1.2 倍）。
2. 醒得太晚就**只丢快照、不丢世界时间**——丢时间的后果是世界永久落后于墙上时钟。

这一节讲的是**服务端**怎么推进时间。**玩家那一侧的时间账**——他看见的世界比
服务端晚多久、判定怎么退回到他看见的那一刻、出拳的 0.3 秒判定窗与冷却缓冲是
怎么回事——另外写了一份：[docs/feel.md](feel.md)。

## 7. 多租户：一个账号跑好几款游戏

租户不是装饰性的字段，是真正的隔离边界，三处各管一层：

| 层 | 机制 | 隔离方式 |
|---|---|---|
| 房间宇宙 | DO 名 = `${tenant}:${roomId}` | 不同租户的房间是两个不同的对象实例 |
| 令牌 | 载荷是 `tenant|playerId|name|exp` 的 HMAC | 令牌里的租户必须等于房间的租户 |
| 配额 | D1 `tenants.rules`，落在 D1 里的 `rules` JSON | 每租户自己的房间数/真人上限/机器人上限 |

前端的 `?tenant=` / `?api=` 让同一个静态包能连不同租户、不同后端
（`web/js/config.mjs`）：**多租户不是后端单方面的事**，前端得能选。
邀请链接里只在租户非默认、或前后端跨域时才带上这两个参数——别人地址栏上的
东西不该跟着传播。

  track.mjs      种子 → 一条路

## 9. 明确的取舍

- **线协议是 JSON，不是二进制**。本书读者首先是架构师：打开 DevTools 就能看懂
  每一帧发了什么，比省下 60% 字节值钱。15 台车 + 车流的快照约 4KB，20Hz 下
  约 80KB/s。
- **房间列表用 4 秒轮询**，不是长连接。列表慢一点没人受伤，为它多维持一条常驻
  连接会把复杂度拉回十年前。
- **快照不做视野裁剪（AOI）**。十五台车全在同一段路上，裁剪省不下多少字节，
  却要让每个客户端维护一份"我看得见谁"的状态。
- **不做回滚式重放（rollback）**。只预测自己 + 命令时间线对账已经足够，
  引入回滚会让所有实体都得可重放，代价远大于收益。
- **身份住在名册里，快照只带短整型的车号**。每帧给十五台车各背一个玩家 id 是
  纯浪费，但这条约定的代价很真实：谁忘了去名册查身份，症状不是报错，而是
  **本地预测永不启动**（别人还在跑，只有你是块石头）。
